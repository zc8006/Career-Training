### MuleSoft 项目整体架构——面试口语版

> 这个项目主要是把旧系统中使用 PHP 实现的 REST、SOAP 接口整体迁移到 MuleSoft。调用方请求 MuleSoft API 后，系统会进行参数校验、数据格式转换和业务处理，再调用后端系统并返回结果。对于 SOAP 接口，还需要处理 XML、WSDL 和协议适配。
>
> 我主要负责旧接口逻辑梳理、API 设计与开发，以及单元测试、集成测试和新旧接口结果对比。

### MuleSoft 项目难点——真实案例

> 在 MuleSoft API 迁移项目中，旧系统使用 PHP 实现 SOAP 接口，并要求迁移前后 WSDL 保持不变。测试时发现 MuleSoft 生成的 XML 响应与旧系统不完全一致，主要涉及 XML 命名空间或节点结构。
>
> 我通过对比新旧响应、检查 WSDL 和相关转换逻辑定位差异，然后调整 MuleSoft 的响应映射和格式。修改后重新进行集成测试和新旧结果对比，最终保证了接口兼容性。

### 本轮 10 句背诵清单

1. 原子性：事务中的操作要么全部成功，要么全部回滚。
2. 一致性：事务执行前后，数据都符合业务规则和约束。
3. MySQL 四种隔离级别是读未提交、读已提交、可重复读、串行化。
4. InnoDB 默认隔离级别是可重复读。
5. 对象通常在堆中，方法中的局部引用变量通常在虚拟机栈中。
6. `equals()` 相等的对象，`hashCode()` 必须相同。
7. Redis 加锁使用 `SET lockKey uniqueValue NX PX expireTime`，解锁时使用 Lua 脚本。
8. 正确拼写是 `@SpringBootApplication`、`@Autowired`、`@Transactional`。
9. Redis 常用于热点缓存、临时数据以及分布式锁或幂等控制。
10. MuleSoft 架构：调用方 → MuleSoft API → 校验与转换 → 后端系统 → 返回结果。

## Self-Growth 模式

### 1. 三个训练阶段

#### 阶段一：原题独立达标

- 只使用福州小厂 30 道原题。
- 一次只问一道，不提前显示答案或关键词。
- 优先抽查首答为 C、首答为 B、尚未重新确认的题。
- 看答案后立即复述正确，只记“引导通过”，不记稳定 A。
- 同一道题需要在不同时间独立回答正确，才记为稳定 A。
- 30 道题未全部成为稳定 A 时，不增加实战扩展。

#### 阶段二：基础保持 + 实战扩展

仅在 30 道原题全部稳定 A 后开启：

- 每次先复习原题，再扩展实战题。
- 扩展只到项目实战级，例如使用场景、排查顺序、方案取舍。
- 不问框架源码、JVM 源码或过深实现细节。
- 每个知识点最多增加 1 个实战追问，仍然一次一道。
- 实战题回答不好时记录为实战薄弱项，不篡改原题掌握记录。

#### 阶段三：模拟面试

- 随机混合 Java、Spring、MySQL、Redis 和项目表达。
- 不提示所属知识点。
- 重点检查是否能先说结论，再补充原理和项目场景。
- 控制追问数量，避免把基础训练变成源码问答。

### 2. 评分标准

| 等级 | 标准 | 后续处理 |
| --- | --- | --- |
| A | 不看答案，能独立、完整、准确地说出面试答案 | 进入随机复习 |
| B | 核心方向正确，但有漏项、术语不准或表达不完整 | 1 天、3 天后复测 |
| C | 不会、答错或原理混乱 | 当场纠正，并在 1 天、3 天、7 天后复测 |
| 引导通过 | 看过答案后能够正确复述 | 不能代替 A，之后必须独立复测 |

### 3. 动态选题规则

每次训练按以下优先级自动选择下一题：

1. 到期的 C 类题
2. 到期的 B 类题
3. 仅“引导通过”、尚未独立达标的题
4. 尚未重新确认的题
5. 已是 A 的随机保持题

同一知识点连续回答错误时，降低表达长度，先掌握基础结论；基础结论稳定后再恢复完整面试表达。

### 4. 专项训练节奏

在阶段一：

1. 每次练习 8～10 道原题。
2. 一次只显示一道。
3. 不临时增加题量。
4. 不做实战扩展和源码追问。
5. 结束时只汇总 A/B/C、引导通过和下次回炉题。

进入阶段二后：

1. 先复习 8 道原题。
2. 再增加不超过 2 道实战题。
3. 追问总数控制在 3～5 个以内。
4. 最后整理 8～10 句背诵清单。

### 5. 项目题约束

- 优先使用真实的 MuleSoft API 迁移与系统集成经历。
- 酒店 PMS、RAG 等内容必须明确说明是实践项目。
- 不编造生产访问量、团队规模、性能数据或个人职责。
- 回答顺序优先使用：背景 → 架构/职责 → 难点 → 解决方案 → 结果。
