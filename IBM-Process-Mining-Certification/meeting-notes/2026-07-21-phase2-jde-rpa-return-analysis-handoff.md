## 1. 最终录入方式的统一口径

最终录入方式必须根据同一 Case 中最后一次 `录入完成` 的执行账号判断：

1. 最后一次 `录入完成` 的 Resource 为 `ChinaBot` / `ChinaBOT` → `RPA_PROCESS`；
2. 最后一次 `录入完成` 的 Resource 为非 ChinaBot 人工账号 → `MANUAL_PROCESS` / `MANUAL_ONLY`；
3. Eventlog 中完全没有 `录入完成` 时，才使用 Tracker 补充判断；
4. Tracker 补充条件：`TrackerStatus = 审批结束` 且 `IBMProcessor = ChinaBot/ChinaBOT`；
5. 仍无法判断 → `OTHER`。

旧逻辑“只要曾经出现过 ChinaBot + 录入完成就判为 RPA”已废弃。

## 2. 新旧分类核验结果

在 OCR Feedback 母集 20,942 件中：

|---|---|---:|

| OTHER | OTHER | 15 |

关键修正：68 件曾经出现过 ChinaBot 录入完成，但最后一次录入完成由人工执行，因此从 RPA 改为人工。

## 5. 1,388 件证据不足组

这 1,388 件全部满足：

- JDE；
- 已确认有人工介入；
- Eventlog 中没有任何 `录入完成`；
- TrackerStatus = 审批结束；
- IBMProcessor = ChinaBot；
- 无法从 Eventlog 证明人工后重新进入 ChinaBot。

审批结束前最后一个非审批 Activity：

| 最后状态 | 执行方 | Case 数 | 占比 |
|---|---|---:|---:|
| 意见征询 | 人工 | 1,082 | 77.95% |
| OCR完成 | 人工 | 306 | 22.05% |

结论：这 1,388 件全部由人工执行最后一个业务动作，随后进入审批结束，但 Eventlog 没有录入完成。可能是 Eventlog 不完整，也可能 `IBMProcessor=ChinaBot` 仅表示 Tracker 归属而非最终录入执行者。

临时命名：**Tracker 标记 ChinaBot，但 Eventlog 显示人工最后处理且无录入完成证据**。

这组暂不纳入明确人工或明确 RPA 的根因结论，需业务确认：

1. JDE 正常由 RPA 完成时是否一定产生 `录入完成`；
2. `IBMProcessor=ChinaBot` 的真实业务含义；
3. Eventlog 是否存在缺失。

## 11. 下一步分析优先级

### 第一优先：484 件直接人工录入

需要拆分：

- 无任何 RERUN 证据；
- Comments 有 RERUN，但无后续 ChinaBot；
- Tracker 留言有 RERUN；
- 有录入错误；
- 有 OCR 待查/有误；
- 无可见异常状态。

目标：判断是没有尝试 Re-run、尝试后未进入机器人、技术失败，还是 Eventlog 缺失。

### 第二优先：251 件意见征询后人工录入

需要结合 Comments / Tracker 原文，归类意见征询原因：

- PO未收货；
- PO号、金额、税率问题；
- 供应商问题；
- 合同或验收问题；
- 预付款问题；
- 客户信息不完整；
- 其他。

目标：区分客户侧可改善问题、可修正后 Re-run 场景和必须人工处理场景。

### 第三优先：17 件回流失败逐件核查

输出 Case 明细：

- UUID；
- 最后 ChinaBot 状态；
- 后续首个人工 Activity；
- 最后一次录入完成账号；
- RERUN 留言；
- Tracker 留言；
- 时间间隔。

## 12. SQL 使用注意事项

- IPM 表格最多显示 150 行；明细查询必须加分类筛选；
- IPM 复杂 SQL 容易报“一般错误”，尽量避免过深嵌套和窗口函数；
- 时间戳展示使用 `sys.epoch(timestamp / 1000)`，如表格仍显示毫秒值，应通过 `EXTRACT + LPAD + 字符串拼接` 强制转成文本；
- `comments_detail_tbl` 的物理字段使用大写 `STATUS`；
- `UPPER(STATUS) LIKE '%RERUN%'` 可识别 RERUN / rerun / 带账号后缀的写法；
- 最终录入方式相关 SQL 必须统一使用“最后一次录入完成执行者”口径。
