# 2026-10-27～28：模拟复盘超时修复与线上验收

## 问题与证据

第 50 版上线后，模拟账户仍更新，但候选复盘一直 pending。10 月 27 日 09:49（北京时间）的实际 API：8,848 个候选、23,872 个已到期待结算点，sampled/missing 均为 0。Worker 日志持续显示 `/api/ingest/simulation` 在约 14.9 秒被取消；VPS 请求超时为 15 秒。

旧流程先提交账户，再串行运行五项研究任务。最后的候选结算先逐条读取 200 个报价，读完才写入结果。被取消后，下一轮重新选择相同 pending 数据，没有持久进度。

## 实施

- 保留账户买卖的原子提交与五分钟防重，不改变 V7.5 交易参数、H1/H2/H3 准入规则及 GMGN-only 来源要求。
- 首次决策及 1h/6h/24h/7d 四个目标在响应前保存；每 50 个候选采用两条 SQL 的原子 batch。
- 使用 `next/server` 的 `after` 执行复盘。已安装 Vinext 0.0.50 的实现通过请求 ExecutionContext 注册 `waitUntil`；Worker 入口已传递该上下文。
- 优先处理目标后 10 分钟窗口内的记录，再运行既有研究，最后清理历史积压。
- 每批最多 100 点，一条索引查询取各点最早合规 GMGN 报价，一条条件更新保存结果；不再逐点往返数据库。
- 当前窗口限 5 批/4 秒；历史限 50 批/8 秒，且在后台启动后 25 秒停止开启新批。预算是批间检查，正在执行的单个数据库调用仍可能超出预算。
- `status='pending'` 条件更新保证重复或重叠请求不覆盖已完成证据；中断后从未完成记录恢复。当前窗口无报价的记录通过本轮游标跳过，不阻塞后面的有报价记录。
- 每个阶段记录实际耗时与结算数量，区分账户提交、HTTP 确认、后台完成，不能再把候选入库当成复盘成功。

## 证据边界

过期点只恢复目标后 10 分钟内已保存的 GMGN 报价。无报价记 missing；有历史报价可记录参考涨跌，净收益仍为 null。处理时重新读取真实时钟，不能用请求开始时刻伪装成按时模型成交。排除旧 `-tracking-` 数据，继续选择最早报价。

后台执行有平台时限，不是无限队列。候选 pending 数据持久存在，后续真实采集轮次继续恢复。新候选保存失败会明确记录 `decisionCapture=failed`；`followup=scheduled` 只说明已调度，不代表已完成。

## 验证

135 项测试通过，TypeScript 检查、生产构建及 `git diff --check` 通过。新增覆盖：

1. 2,400 个旧点与 130 个新点混合，新点优先且每百点两个数据库往返。
2. 第二批写入前注入故障，首批 100 点保留，重试只补余下 150 点。
3. 慢数据库触及预算后停批，未来目标保持 pending。
4. 无报价新点不挡后续可结算点；并发运行只结算一次。
5. 查询跨越宽限期后，不用旧时钟补造净收益。
6. 实际模拟路由先返回再执行后台研究，后台不改变模拟现金；重复轮次不重复买入或调度。

上线验收另需真实采集轮次证明：请求成功、历史积压下降、当前窗口完成结算。构建成功本身不满足验收。

参考：[Next.js after](https://nextjs.org/docs/app/api-reference/functions/after)、[Cloudflare waitUntil](https://developers.cloudflare.com/workers/runtime-apis/context/)。

## 第一轮线上验收与进一步优化

第 51 版 10:05:16（北京时间）发布。10:08:56 的真实 VPS 请求：账户提交 3,116ms，首次决策保存并确认响应 3,718ms；3 个当前窗口点与 100 个历史点已真实完成，Worker 最终状态 ok / HTTP 200。含后台工作的 wallTime 19,637ms 不是 HTTP 响应耗时，后台完成 15,917ms。

但历史 100 点耗时 9,418ms，仍不足以快速清理积压。继续按 35,000 条 pending 的规模检查 SQL 执行计划，发现 UPDATE FROM 内联 json_each 会先遍历所有 pending，再逐一匹配 JSON，复杂度随整个队列增长。将本批 ID 显式 MATERIALIZED 后，执行计划改为从批次遍历并用点的主键查找。相同本地 35,000 点夹具的写入从约 2,427ms 降至约 0.67ms；这是本地基准，不冒充线上耗时。

增加回归测试，强制验证生产规模下走 id 查找而非 pending 全集与 JSON 的笛卡尔比较。后台指标新增 quoteReadMs/writeMs；第 52 版还需后续真实请求核验吞吐。

此次补充教训：边界测试和往返次数不足以证明生产规模性能；必须验证 SQL 实际访问路径、真实数据量及上线后的每阶段耗时。发现瓶颈继续修正，不把“开始落库”当成性能问题已经全部消除。
