## 核心记忆

1. ACID 是原子性、一致性、隔离性、持久性。
2. 持久性是事务提交后结果永久保存，系统重启也不应丢失。
3. `tryLock(2, TimeUnit.SECONDS)` 返回 `true` 后才能执行业务和解锁。
4. `tryLock()` 返回 `false` 时，当前线程没有获得锁，不能调用 `unlock()`。
5. `EXPLAIN` 关注 `type`、`possible_keys`、`key`、`rows`、`Extra`。
6. 线程池处理顺序是核心线程、任务队列、最大线程、拒绝策略。
7. 线程池七个参数包括核心线程数、最大线程数、存活时间、时间单位、任务队列、线程工厂和拒绝策略。
8. Redis 锁提前过期可能导致多个线程同时执行业务。
9. Redis 分布式锁可通过合理过期时间、自动续期和业务幂等降低风险。
10. MyBatis 包含式模糊查询使用 `LIKE CONCAT('%', #{param}, '%')`。

### Outbox 两阶段解释与巩固

本轮主要误区：把“消息写入数据库表”与“消息发送到消息队列”混为一步，以及认为后台会在订单保存失败后重新执行订单创建。

示例：订单1001购买商品A一件，需发消息通知库存服务扣减。

| 阶段 | 操作或失败情况 | 正确处理 |
| --- | --- | --- |
| 保存阶段，事务提交前 | 同事务写订单表和本地消息表 | 订单1001与“请扣库存”的待发送消息一起保存 |
| 保存阶段，事务提交前 | 订单保存失败 | 整个事务回滚，不保留待发送消息，不通知库存扣减 |
| 保存阶段，事务提交前 | 订单写入成功，但消息写表失败 | 整个事务回滚，订单也不保留 |
| 保存阶段 | 两条记录都保存成功 | 提交事务，订单正式创建，消息等待发送 |
| 发送阶段，事务提交后 | 后台扫描待发送记录并发往消息队列 | 执行的是发送消息，不是重新创建订单 |
| 发送阶段，事务提交后 | 消息队列宕机或发送失败 | 订单已提交，保留消息记录，后台重发 |
| 发送阶段 | 收到发送成功确认 | 标记消息已发送；这不等于库存业务已经消费成功 |
| 发送阶段 | 超过最大重试次数 | 告警并保留记录供后续处理；补发可能重复，消费者仍需幂等 |

### 本轮库存补偿缺口

本轮已经能把补偿记录与恢复库存放在同一事务，未再说成与扣减库存同事务。“回滚库存”应规范为新的补偿操作：加回已扣库存，而不是由订单本地事务撤销远程已提交事务。

完整流程：

1. 订单明确失败后，通过可靠消息或持久化补偿任务触发库存恢复，不能只依赖一次远程调用。
2. 库存服务以订单号作为补偿业务唯一标识；插入补偿记录与加回库存放在同一本地事务中。
3. 重复补偿不再加回；加回失败时补偿记录也回滚，允许后续重试。
4. 补偿消息或任务失败继续重试，超过最大次数保留记录并报警，供后续处理。
5. 补偿任务不能随失败的订单创建事务一起回滚；需可靠保留任务来源。

记忆句：**可靠触发 → 补偿记录与加回库存同事务 → 唯一约束防重复 → 失败重试、超限保留告警。**

### Outbox 两阶段顺序保持

- 保存阶段：订单和待发送消息同事务，任一写入失败一起回滚；都写入成功后提交，此时消息仍为待发送。
- 发送阶段：后台扫描待发送及可重试失败记录；收到消息队列发送成功确认后才标记已发送，不能在订单提交时直接标记成功。
- 发送失败：保留消息、记录次数并重试；超过最大次数告警并保留失败数据。
- 发送成功不等于消费者业务完成，消费者仍需幂等。

### 新实战组答案要点

#### 1. 并发扣库存避免超卖（B）

不同订单可同时读到库存1，单靠先查后扣或订单号唯一约束不能防止超卖。把条件判断和扣减放在同一条 SQL：

```sql
UPDATE product
SET stock = stock - 1
WHERE id = #{id} AND stock >= 1;
```

检查受影响行数：1表示本次扣减成功，0表示未扣减成功，不能继续按下单成功处理。购买数量为 qty 时，先校验 qty 为正数，再用 stock >= qty 和 stock = stock - qty。订单幂等与库存不超卖解决的是不同问题。

#### 2. 数据库提交后删除缓存失败（A）

会继续读取旧缓存。重试删除，并用合理过期时间兜底。需要可靠重试时，将删除任务持久化或通过可靠消息/变更日志驱动删除，避免进程退出后丢失任务。数据库已提交，不能依赖回滚已提交的事务解决。

#### 3. 第三方接口超时与重试（B）

超时参考正常耗时和业务等待上限，分别设置连接超时、响应读取超时。临时网络故障或部分服务暂时不可用时，在接口允许且操作可安全重试的前提下，设置间隔、最大次数和整体时间上限。参数错误、鉴权失败、明确业务失败应先修正原因。创建订单、扣款等操作超时结果未知，先查询结果，或确保使用同一幂等标识后再重试，不能盲目重复执行。

#### 4. 批处理失败恢复与幂等（C，讲解后学习）

核心：分批提交、保存进度、失败重试、保证幂等。

例如每100条作为一批，第5000条所在批次失败时回滚该批，前面已提交批次保留。进度必须持久化，并与对应业务更新保持一致：同一数据库场景中，批次业务结果和进度/成功记录放同一事务提交，避免进度先保存导致跳过，或业务成功但进度未保存导致重复执行。重启后从最后成功提交位置继续，失败批次重做；用业务唯一标识或处理记录防重复。失败有限重试，超限保留失败记录并报警。涉及外部系统副作用时仍需对方支持幂等或查询确认，不能只靠本地进度。

### 复习答案卡

#### 1. Linux 命令

ps 查看进程，cat 查看文件，tail 查看末尾。查看日志最后200行并持续观察新增内容：

```bash
tail -n 200 -f application.log
```

#### 2. AI 工具使用

回答顺序：工具 → 真实任务 → AI 提供的帮助 → 自己如何验证。已知真实习惯是使用 ChatGPT/Codex 确认问题和 review；下次补充一件本人确实做过的具体任务，以及实际使用的核对、运行或测试方式。另一轮 AI review 不能代替自己验证，不为用户虚构案例。

#### 3. MyBatis-Plus 分页

分页插件通过拦截器，根据页码和每页条数改写 SQL，实现物理分页，例如 MySQL LIMIT offset, size；通常再执行 COUNT 查询总数，返回当前页数据与总数等分页信息。不要求背源码。

#### 4. 数据结构与 HashMap

常见结构：数组、链表、栈、队列、哈希表、树、堆、图。ArrayList 是动态数组，LinkedList 是双向链表；HashMap 采用数组，桶内使用链表或红黑树。扩容扩大数组，树化是符合条件时把桶内链表转成红黑树。

#### 5. 同名学生去重并保留首次顺序

一种方案是 Student 按姓名同时实现 equals 和 hashCode，按原顺序加入 LinkedHashSet，再转换为 List。另一种更局部的方案是遍历原列表，用 HashSet<String> 记录姓名，只有首次出现时把当前学生加入结果列表；不必改变 Student 的全局相等规则。

#### 9. 防超卖

```sql
UPDATE product
SET stock = stock - 1
WHERE id = #{id} AND stock >= 1;
```

判断库存和扣减放在同一条 SQL 内。受影响1行表示扣减成功，0行表示未成功，不能继续按下单成功处理。订单号唯一约束解决重复扣减，不能独自解决不同订单的并发超卖。

#### 10. 第三方接口超时与重试

结合正常耗时和业务等待上限，分别设置连接超时、响应读取超时。对可安全重试的临时故障设置重试间隔和最大次数，控制总体等待时间；参数错误、鉴权失败或明确业务失败先修正原因。创建订单等操作超时结果未知，先查询结果，或确保沿用同一幂等标识再重试。

#### 11. 批处理恢复与幂等

分批处理、每批单独事务；对应业务更新与进度/成功记录放在同一数据库事务内提交。失败批回滚，已提交批保留；重启从最后成功提交的位置恢复，通过业务唯一标识或处理记录保证幂等。失败有限重试，超限保留记录并报警。若包含远程调用，仍需对方幂等或查询确认，不能仅依赖本地事务。

### 唯一未通过实战：业务更新与成功进度一起提交

本轮原答：“分批提交到数据库，下次从失败开始往后继续执行，在业务里增加幂等判断，并且放在同一个事务里。”

缺口不是不懂分批，而是未明确“进度保存在哪里”和“哪两部分在同一事务”。需要主动说清：

1. 每批单独事务，将该批业务更新与成功进度/处理记录写入同一数据库事务。
2. 一起提交或一起回滚；不能只把业务数据入库，进度留在内存。
3. 重启后读取数据库中的最后成功提交位置，重做失败批次；不是从某条报错语句后跳过继续。
4. 用业务唯一标识或处理记录保证幂等，避免恢复时重复产生业务效果。

例如每100条一批，1～4900已提交，4901～5000批次中途失败，则整批回滚，持久化进度仍为4900。重启从4901开始重新处理。

面试简答：

> 我会分批处理，每批业务更新和成功进度记录在同一个数据库事务中提交。失败时回滚当前批，已成功的批次保留；重启后读取持久化进度，从最后成功提交的位置继续，同时用业务唯一标识保证幂等。失败有限重试，超限保留记录并报警。
