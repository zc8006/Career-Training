## 1. 项目与业务目标

项目：`Retail_Status_Process_Test [IBM_Retail_Demo]`

业务目标不是单纯展示流程，而是解决这些问题：

1. 审批以外为什么还有人工参与？
2. 人工参与主要集中在哪些 Activity？
3. 哪些人工参与是正常业务例外，哪些是机器人/RPA流程失败后的人工介入？
4. 哪些路径可以通过规则、OCR、RPA或流程设计优化来减少人工？
5. 最终目标是提升 ChinaBot / 机器人处理比例。

已确认业务口径：

- `ChinaBot` / `ChinaBOT` 是机器人。
- 审批相关必须由人做。
- 审批以外业务希望尽量由机器人完成。
- `RPA范围外` 是 Case 状态，不代表机器人完成处理；通常表示机器人/系统判断该 Case 不适合 RPA 自动处理，后续应转人工。
- “机器人完成录入”业务上意味着应尽量全程机器人完成；如果审批以外还出现人工，需要分析原因。
- Phase1 / Phase2 的 ID 不会重复，不能做同一 Case 的前后对比，只能做阶段总体对比。
- Phase1 第一批数据没有 DDD；Phase2 有 DDD，因此 Not DDD 是重要比较口径。
- 业务背景：发票信息通过 OCR 识别，确认后录入 SAP。中途 RPA 供应商有变化，前后 status 可能不同，需要业务确认哪些状态可等价比较。

## 11. 问题解决方向

### A. 意见征询导致大量录入完成前人工介入

数据：

```text
意见征询 -> 录入完成：1,667
中位：2天16小时
意见征询 Human 100%
```

解决方向：分类统计意见征询原因；对高频可规则化原因建立自动判断/自动补全规则；对低风险场景减少人工征询；对必须人工的场景建立例外清单。

会议问题：意见征询通常因为什么触发？字段缺失、OCR不确定、供应商问题、金额/PO匹配问题，还是业务规则要求？哪些原因有机会规则化？

### B. RPA范围外后大量进入录入完成

数据：

```text
RPA范围外 -> 录入完成：677
中位：11小时40分钟
RPA范围外状态本身主要 ChinaBot 标记
```

解决方向：拆分 RPA范围外 原因类型；找出可回收进 RPA 范围的场景；不能自动化的范围外 Case 定义为合法人工例外；如果范围外判断规则过严，优化规则以提高机器人覆盖率。

会议问题：RPA范围外后进入录入完成的 Case，主要是哪类范围外原因？哪些能通过规则调整、OCR字段补充、供应商主数据维护或 RPA 脚本扩展重新纳入自动处理范围？

### C. 录入中发生错误后仍能完成录入

数据：

```text
录入中发生错误 -> 录入完成：549
中位：19小时27分钟
录入中发生错误 Robot 100%
```

解决方向：区分错误类型；临时错误做自动重试；字段格式错误做前置校验和自动修正；主数据缺失提前校验并推送维护；必须人工的错误进入异常队列并缩短处理时间。

会议问题：这些 Case 是机器人自动重试成功，还是人工处理后完成？主要错误类型有哪些？哪些可以通过前置校验、自动重试或规则修正减少人工？

### D. OCR结果待查 / 结果待查导致录入完成前等待

数据：

```text
OCR结果待查 -> 录入完成：618
结果待查 -> 录入完成：339
OCR结果待查 -> OCR结果待查：47,724
中位约 30 分钟
```

解决方向：区分真实业务待查和系统重复写入；如果是日志重复，后续分析要去重或合并；如果是真实待查，拆原因并寻找自动补全/规则判断机会；对长时间待查建立 SLA 或提醒。

会议问题：待查期间主要发生了什么？系统定时重试、人工确认、等待外部信息，还是重复状态写入？哪些待查原因可以自动化处理？

### E. OCR完成真实含义不清

数据：

```text
OCR完成 Human 100%
OCR待处理 -> OCR完成 只有 1 次
OCR完成 -> 审批结束 1,404
OCR完成 -> 录入完成 295
```

解决方向：确认 OCR完成 的真实业务含义。如果它是人工确认/回写状态，就不能按“系统 OCR 自动完成”理解；如果它应该是系统状态，则需要解释为什么人工账号占比几乎 100%。

2. RPA范围外后续路径：看 RPA范围外 -> 录入完成 / 意见征询 / 废弃删除 / 审批结束 / OCR结果有误。判断哪些是正常人工路径，哪些可优化。
3. 录入中发生错误原因和恢复机制：看错误后的后继路径，判断自动重试还是人工修复。
4. OCR结果待查重复写入：确认是系统定时检查/重复写入还是实际业务待查。
5. OCR完成含义确认：确认其是否为人工确认/回写状态。
