# Retail_Status_Process 问题解决导向接续整理（2026-07-03）

## 1. 业务目标

项目：Retail_Status_Process_Test [IBM_Retail_Demo]

业务目标不是单纯展示流程，而是解决这些问题：

1. 审批以外为什么还有人工参与？
2. 人工参与主要集中在哪些 Activity？
3. 哪些人工参与是正常业务例外，哪些是机器人/RPA流程失败后的人工介入？
4. 哪些路径可以通过规则、OCR、RPA或流程设计优化来减少人工？
5. 最终目标是提升 ChinaBot / 机器人处理比例。

已确认口径：ChinaBot / ChinaBOT 是机器人；审批相关必须由人做；审批以外希望尽量机器人做；RPA范围外是 Case 状态，通常表示机器人/系统判断该 Case 不适合 RPA 自动处理，后续应转人工。

## 3. RPA范围外当前结论

已做表：过滤 activity = RPA范围外，维度 resource，度量 COUNT DISTINCT caseid。

结果：ChinaBot 1412，CNVISY83 1。

正确解释：RPA范围外状态几乎全部由 ChinaBot 写入，但这不代表机器人实际处理了范围外 Case。更合理的理解是 ChinaBot / 系统负责判断并标记该 Case 不在 RPA 自动处理范围内。被标记为 RPA范围外 后，后续业务上应转人工处理。

PPT可写：RPA范围外状态主要由 ChinaBot 标记，说明该状态更像系统/RPA的自动判断结果，而非人工处理动作本身。后续分析重点应转向：RPA范围外之后是否进入人工处理，以及这些后续路径是否合理。

## 4. 最有价值的新发现：录入完成前置路径分析

用户已打开 IBM Process Mining 的活动关系，选择“先行作业 -> 录入完成”。这表示哪些 Activity 最常流向录入完成。

主要结果：

| 前置 Activity | 转换次数 | 平均过渡时间 | 中位过渡时间 |
|---|---:|---:|---:|
| 意见征询 | 1667 | 9天21小时 | 2天16小时 |
| RPA范围外 | 677 | 1天8小时 | 11小时40分钟 |
| OCR结果待查 | 618 | 2天 | 2天9小时 |
| 录入中发生错误 | 549 | 1日10小时 | 19小时27分钟 |
| 结果待查 | 339 | 2天17小时 | 2天12小时 |

| OCR结果有误 | 148 | 2天2小时 | 1日6小时 |

核心结论：录入完成不是单一路径到达，而是多个人工、异常、待查状态的汇合点。

PPT标题建议：录入完成前置路径分析。

PPT结论建议：录入完成是多个路径的汇合点，前置来源包括意见征询、RPA范围外、OCR结果待查、录入中发生错误等。这说明录入完成前存在人工确认、范围外处理、待查处理和异常恢复路径。后续优化不应只看录入完成比例，而应拆解这些前置来源，判断哪些路径可以减少人工介入或提升自动恢复能力。

## 5. 问题解决方向

### A. 意见征询导致大量录入完成前人工介入

数据：意见征询 -> 录入完成 1667，中位 2天16小时。

要解决：分类统计意见征询原因；对高频可规则化原因建立自动判断/自动补全规则；对低风险场景减少人工征询；对必须人工的场景建立例外清单。

会议问题：意见征询通常因为什么触发？字段缺失、OCR不确定、供应商问题、金额/PO匹配问题，还是业务规则要求？哪些原因有机会规则化？

### B. RPA范围外后大量进入录入完成

数据：RPA范围外 -> 录入完成 677，中位 11小时40分钟。

要解决：拆分 RPA范围外 原因类型；找出可回收进 RPA 范围的场景；不能自动化的范围外 Case 定义为合法人工例外；如果范围外判断规则过严，优化规则以提高机器人覆盖率。

会议问题：RPA范围外后进入录入完成的 Case，主要是哪类范围外原因？哪些能通过规则调整、OCR字段补充、供应商主数据维护或RPA脚本扩展重新纳入自动处理范围？

### C. 录入中发生错误后仍能完成录入

数据：录入中发生错误 -> 录入完成 549，中位 19小时27分钟。

要解决：区分错误类型；临时错误做自动重试；字段格式错误做前置校验和自动修正；主数据缺失提前校验并推送维护；必须人工的错误进入异常队列并缩短处理时间。

会议问题：这些 Case 是机器人自动重试成功，还是人工处理后完成？主要错误类型有哪些？哪些可以通过前置校验、自动重试或规则修正减少人工？

### D. OCR结果待查 / 结果待查导致录入完成前等待

数据：OCR结果待查 -> 录入完成 618；结果待查 -> 录入完成 339；此前看到 OCR结果待查 -> OCR结果待查 自循环 47724 次，中位约 30 分钟。

要解决：区分真实业务待查和系统重复写入；如果是日志重复，后续分析要去重或合并；如果是真实待查，拆原因并寻找自动补全/规则判断机会；对长时间待查建立 SLA 或提醒。

会议问题：待查期间主要发生了什么？系统定时重试、人工确认、等待外部信息，还是重复状态写入？哪些待查原因可以自动化处理？

## 6. 下一步分析排序

1. 人工录入完成的来源拆解：继续用活动关系 -> 先行作业 -> 录入完成。按意见征询、RPA范围外、录入中发生错误、OCR结果待查/结果待查四类拆。
2. RPA范围外后续路径：看 RPA范围外 -> 录入完成 / 意见征询 / 废弃删除 / 审批结束 / OCR结果有误。判断哪些是正常人工路径，哪些可优化。
3. 录入中发生错误原因和恢复机制：看错误后的后继路径，判断自动重试还是人工修复。
4. OCR结果待查重复写入：确认是系统定时检查/重复写入还是实际业务待查。
