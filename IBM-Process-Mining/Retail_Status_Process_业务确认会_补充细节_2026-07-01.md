## 7. To-Be BPMN 画法细节

### 菱形与活动框

用户问过：`处理后完成` 和 `无法处理` 是不是应该是菱形。

结论：

- `处理后完成`、`无法处理` 不应该是活动框。
- 它们更适合作为网关后的分支标签。
- 真正的菱形应该是：`异常是否可处理？`
- `录入中发生错误` 是数据里的 Activity，可以作为矩形活动框。
- `录入完成`、`废弃删除` 是数据里的 Activity，可以作为矩形活动框。

推荐片段：

```text
结果待查
↓
是否发生录入异常？
├─ 否 → 录入完成
└─ 是 → 录入中发生错误
        ↓
      异常是否可处理？
      ├─ 是 / 处理后完成 → 录入完成
      └─ 否 / 无法处理 → 废弃删除
```

### RPA范围外后面的画法

用户卡在 RPA范围外和录入异常区域。

建议不要强行画复杂，要拆成两个区域：

左侧：RPA范围外分支

```text
是否满足RPA/OCR处理规则？
├─ 是 → OCR待处理
└─ 否 → RPA范围外 → 是否可转人工处理？
                     ├─ 是 → 录入完成
                     └─ 否 → 废弃删除
```

右侧：录入异常分支

```text
结果待查
↓
是否发生录入异常？
├─ 否 → 录入完成
└─ 是 → 录入中发生错误 → 异常是否可处理？
                         ├─ 是 → 录入完成
                         └─ 否 → 废弃删除
```

审批部分：

```text
录入完成
↓
是否进入审批相关流程？
├─ 否 → End
└─ 是 → 是否需要意见征询？
        ├─ 是 → 意见征询
        └─ 否
        ↓
      审批结果判断
      ├─ 通过 → 审批结束 → End
      ├─ 拒绝 → 审批拒绝 → End
      └─ 废弃 → 废弃删除 → End
```

### 审批结束等终点

建议：

- `审批结束`、`审批拒绝`、`废弃删除` 都直接接 End。
- 不要让线绕大圈。

## 8. 颜色标注细节

用户问是否需要标注哪些人工、哪些不是人工。

建议：需要标注，但不要复杂。用三类颜色：

```text
蓝色：人工主导
灰色：系统/非人工主导
橙色：混合状态
黄色菱形：业务判断网关
```

节点建议：

```text
人工主导：OCR完成、意见征询、审批结束、审批拒绝、废弃删除
系统/非人工主导：OCR待处理、OCR结果有误、OCR结果待查、结果待查、录入中发生错误、OCR待处理/错误、RPA范围外
混合：录入完成
```

特别说明：

- `录入完成` 不要涂成人工蓝色，虽然人工参与率高，但仍有非人工参与，建议橙色。
- `RPA范围外` 不要涂成人工蓝色。它本身是系统/非人工记录为主，应灰色；后续线可以标注“转人工处理”。
- 不建议把线也改颜色，只改活动框颜色即可，避免流程图太乱。

## 9. 对 RPA范围外的反复讨论

用户认为：`RPA范围外` 不应该是人工做吗？

解释：

- 从业务含义看，RPA 范围外通常意味着机器人不能处理，后续可能转人工。
- 但从 eventlog.resource 数据看，`RPA范围外` 这个状态本身几乎全是非人工账号记录：

```text
RPA范围外 Total Case: 1,415
Human Case: 1
Human Rate: 0.07%
Robot/System Case: 1,415
Robot/System Rate: 100%
```

因此应区分：

```text
RPA范围外 = 系统判断结果
RPA范围外之后的处理 = 可能转人工
```

图上建议：

```text
RPA范围外：灰色，标注“系统判断”
RPA范围外 → 录入完成：连线标注“转人工/人工处理”
录入完成：橙色，标注“混合，人工为主”
```

## 10. OCR完成的特殊性

用户发现 `OCR待处理 → OCR完成` 只有 1，觉得很怪。

解释：

- 图上的 `1` 是两个节点之间的直接转换次数，不是 `OCR完成` 的总件数。
- `OCR完成` 节点本身显示有大量事件/记录。
- 后续查看活动关系后确认：`OCR完成` 的直接前驱主要不是 `OCR待处理`。

OCR完成的前驱很多来自：

```text
录入完成
意见征询
结果待查
录入中发生错误
OCR结果待查
OCR完成自身循环
审批拒绝
OCR结果有误
RPA范围外
```

所以 `OCR完成` 可能更像：

```text
人工确认完成 / OCR相关处理完成 / 补充处理完成
```

而不是单纯的系统 OCR 自动完成。

业务确认问题：

```text
OCR完成到底是系统 OCR 完成，还是人工确认 / 补充处理完成？
```

## 11. 线数字与节点数字不一致的问题

用户发现汇总到 `录入完成` 和实际件数不一样。

解释：

- 节点上的数多是 Activity 节点的 Case 数或事件数/去重 Case 数，取决于视图设置。
- 线上的数字通常是活动转换次数。
- 一个 Case 可能多次进入 `录入完成`，也可能通过多条路径进入或回到 `录入完成`。
- 因此不能把前面分支的线数字相加去对 `录入完成` 节点数。

会议表达：

```text
这里我们不把各条线的数量相加，而是用它判断流程关系。结果待查、录入异常、RPA范围外等路径都可能进入或回到录入完成，所以录入完成是关键汇合节点，但不是简单加总节点。
```

## 13. 关于“PPT 问题能不能明白整个业务”

用户问：PPT 这些问题都回答了，是不是就能明白整个业务？

回答结论：

- 能明白大框架和关键口径。
- 不能完全明白整个业务。
- PPT 是业务确认会材料，不是最终业务分析报告。

PPT 要确认：

```text
每个 Activity 的业务含义
哪些节点人工处理
哪些节点系统/机器人判断
哪些是正常路径
哪些是异常/待查/废弃
哪些路径业务允许存在
哪些路径看起来不合理
```

后续真正业务问题要通过偏差 Case 分析：

```text
哪些 Case 偏离标准流程
偏离 Case 集中在哪些原因
哪些账号/系统/供应商/单据类型问题最多
偏差是否导致处理时间变长
偏差是否导致废弃删除、审批拒绝、重复待查增加
```

核心理解：

```text
拿业务认可的标准流程，去对比 eventlog 里实际 Case 的流转偏差。
```
