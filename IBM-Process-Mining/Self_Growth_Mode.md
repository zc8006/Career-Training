# 自我成长模式

这个模式不是只把 SQL 跑通，而是让每次分析都沉淀成下一次可复用的能力。

## 一轮分析的七个步骤

### 1. 明确业务问题

先写清楚业务问题，不直接从图表或 SQL 开始。

示例：

- BOT 在哪里转为人工？
- 人工处理后是否重新回到 BOT？
- 回到 BOT 后是否真正完成录入？
- 哪些 Comments 或 OCR Feedback 对应可修复的自动化缺口？
- 哪些场景属于业务例外，不应被算作 RPA 提升机会？

### 2. 固定统计口径

每次都明确：

- 基数是什么：Case、事件行、Status 行还是去重 UUID
- 是否排除 DDD
- 是否限定 Phase1 / Phase2
- 是否按 `OCR_FEEDBACK`、System、Request Type 等筛选
- 同一 UUID 是否允许进入多个分类
- 百分比分母是什么
- “回到 BOT”和“BOT 最终成功”是否分开定义

本轮得到的重要教训：

```text
人工后出现任意 BOT 活动
≠ BOT 恢复成功
≠ BOT 最终录入完成
```

必须把三者拆开。

### 3. 建立分析链路，而不是孤立图表

推荐顺序：

```text
总体结果
→ 路径转化
→ 最终状态
→ Comments 原因
→ OCR Feedback
→ System / PO / QA / 电子签章 / Rework
→ 改善机会
```

单独的 Comments Top10 或 OCR Feedback 饼图只能描述现象，只有与流程结果关联后，才能解释业务原因。

### 4. 提出可验证假设

先写出可验证的判断，例如：

- 人工“录入完成”属于流程终点，不应进入 BOT 回归率分母。
- 意见征询可能是协同节点，不一定是根因。
- OCR完成后的 Case 比意见征询后的 Case 更容易回到 BOT。
- 人工后重新回到 BOT 的 Case 中，大量 Case 仍会停在录入错误或意见征询。
- PO 对比、QA、电子签章、收货和系统修改可能是 BOT 二次失败的主要原因。

### 5. 用 SQL 或预计算表验证

SQL 输出应根据问题选择：

- 分类
- Case 数或 Status 行数
- 占比
- 路径转化数
- 最终状态
- 平均或中位处理时长
- Rework 率
- 最终 RPA 成功率

原则：

- 具体规则优先，通用规则靠后。
- 使用 `LIKE / NOT LIKE` 时防止同一 Status 重复命中。
- 关联属性表时先对 UUID 去重，避免 JOIN 放大。
- IPM 2.0.3 中避免使用 `WITH`。
- 大量事件自关联、相关子查询和时间比较容易超时。
- 对路径先后关系，可在 Excel Power Query 或数据源端生成 Case 级辅助表，再导入 IPM。

本轮新增辅助表：

```text
bot_recovery_case_tbl
```

核心字段：

```text
UUID
HAS_MANUAL_INTERVENTION
FIRST_MANUAL_TIME
FIRST_BOT_TIME
LAST_BOT_TIME
HAS_MANUAL_TO_BOT
HAS_MANUAL_TO_BOT_ENTRY
HAS_BOT_TO_MANUAL
HAS_BOT_MANUAL_BOT
```

### 6. 校验结果

至少做以下检查：

1. 分类合计是否符合预期基数。
2. 同一 Status 是否重复命中。
3. JOIN 前后件数是否被放大。
4. Excel 与 IPM 的统计口径是否一致。
5. 所有组件是否使用相同的 Phase 过滤器。
6. 最终状态各分类合计是否等于总 Case 数。
7. 时间字段是否能正确比较。
8. 同一最大时间点存在多条 Activity 时，是否导致 Case 重复归类。

本轮典型问题：

- 不同组件一个使用 `phase2`，另一个使用“无”，造成分子分母错位。
- 把人工录入完成放入“可回归人工 Case”分母，导致回归率被压低。
- 只用 BOT“录入完成”定义 BOT 时间，导致 `BOT → MANUAL → BOT` 全部为 0。
- 最后一个 BOT 时间点有多条 Activity，导致最终状态合计大于总 Case。

### 7. 从结果走向改善建议

每个分析结果至少落到三类建议：

#### 业务规则

- 哪些场景必须人工确认？
- 哪些审批、QA、收货或电子签章规则可以标准化？
- 哪些场景应明确排除在 RPA 范围之外？

#### 系统与数据

- OCR Feedback 是否暴露识别或阈值问题？
- PO、OU、供应商、金额、收货信息是否可以提前校验？
- BOT 报错后是否缺少可重试机制或明确错误码？

#### 流程设计

- 人工处理后是否有机制重新触发 BOT？
- 意见征询结束后是否能自动回流？
- 人工修改 PO、补充收货或完成电子签章后，是否需要重新排队执行？

## 本轮 Phase2 路径分析沉淀

### 已验证数据

- 人工介入 Case：12,504
- 排除明显终点活动后的可回归人工 Case：4,902
- 可回归人工 Case 中重新出现 BOT：328，6.691%
- 全部人工后回 BOT：337
- 337 件的最终 BOT 状态：
  - 录入中发生错误：116，34.421%
  - 录入完成：92，27.299%
  - 意见征询：84，24.925%
  - 其他异常或待查：45
- 真正人工处理后由 BOT 录入完成：92 / 4,902，约 1.877%

### 分析意义

这组数据说明：

- “BOT 再次出现”不是最终成功。
- 人工后真正恢复自动录入的比例很低。
- 提升 RPA 不能只看总体人工原因 Top10。
- 必须锁定最终失败 Case，再关联 Comments、OCR Feedback、System、PO、QA、电子签章和 Rework。
- 分析最终目标是找到“修复一类问题可以增加多少 BOT 成功 Case”。

## 成长循环

```text
发现问题
→ 明确口径
→ 建立分析链路
→ 写 SQL / 预计算
→ 校验
→ 用 Comments 和 OCR Feedback 解释
→ 提出业务、系统、流程建议
→ 估算提升机会
→ 沉淀方法
→ 下一轮提出更好的问题
```

## 当前项目的成长重点

- 从“展示件数”升级到“解释影响”。
- 从“单一分类图”升级到“路径 × 最终状态 × Comments × OCR Feedback × Rework”。
- 从“SQL能运行”升级到“口径可验证、逻辑可复用、性能可接受”。
- 从“人工后出现 BOT”升级到“BOT 是否最终成功”。
- 从“发现异常”升级到“给出业务、系统、流程三类改善建议，并估算提升 Case 数”。
