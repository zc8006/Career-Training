# 自我成长模式

这个模式不是只把 SQL 跑通，而是让每次分析都沉淀成下一次可复用的能力。

## 一轮分析的八个步骤

### 1. 先定义真正的业务问题

不要从“做哪张图”开始，而要从“客户要做什么决定”开始。

本项目的真正问题不是：

```text
人工比例是多少？
```

而是：

```text
为什么一开始不能 RPA？
人工处理后做了什么？
为什么有些 Case 能 rerun 成功，有些再次失败或停滞？
修复哪一类问题最能提升 RPA？
```

### 2. 分开两条因果链

#### 初始不能 RPA

重点字段：

- OCR Feedback
- System
- Request Type
- PO Result
- PO Match Result
- 票据类型、阈值、格式差异

OCR Feedback 的职责是解释“为什么一开始不能直接 RPA”，不是解释“为什么 rerun 失败”。

#### 人工后 rerun

重点字段：

- 人工 Activity
- Comments 原因分类
- 是否更改 PO、补收货、完成电子签章、通过 QA
- 是否重新触发 BOT
- 最后一个 BOT Activity
- Reworks

这条链路解释：

```text
人工做了什么
→ 是否回到 BOT
→ 最终成功 / 失败 / 停滞
```

不能把两条链混在一起。

### 3. 固定统计口径

每次明确：

- 基数是 Case、事件行、Status 行还是去重 UUID
- 是否排除 DDD
- 是否限定 Phase1 / Phase2
- 分母是否包含终点 Activity
- 同一 UUID 是否允许进入多个分类
- “出现 BOT”“回到 BOT”“最终 BOT 成功”分别如何定义
- Comments、OCR Feedback 是否覆盖全部 Case

本轮最重要的口径认识：

```text
人工后出现任意 BOT 活动
≠ rerun 成功
≠ 最终 BOT 录入完成
```

### 4. 先构造流程漏斗，再做根因分析

推荐顺序：

```text
总体 RPA / 人工结果
→ 发生人工介入
→ 可回归人工 Case
→ 人工后重新出现 BOT
→ 最终 BOT 状态
→ SUCCESS / FAILED / STALLED
→ 再关联 Comments、业务属性与人工动作
```

不要先做 Comments Top10 或 OCR Feedback 饼图。先锁定流程结果组，再解释原因。

### 5. 提出可验证假设

示例：

- 人工“录入完成”属于流程终点，不应进入回归率分母。
- 意见征询和 OCR完成是最主要的可回归人工节点。
- 人工后回 BOT 的主要问题不是没有重启，而是重启后仍失败或停滞。
- PO号码/OU、QA、收货问题更容易再次失败。
- 电子签章、金额/单价和类型匹配更容易停在意见征询。
- 成功组可能不产生 Comments，因此 Comments 主要解释失败和停滞。

每个假设必须有可验证的分子、分母、路径条件和对照组。

### 6. 选择合适的数据处理层

IPM 适合展示和交互分析，但不适合反复执行复杂事件自关联。

本轮采用：

```text
Excel Power Query
→ 生成 Case 级 bot_recovery_case_tbl
→ 上传 IPM
→ 用简单 JOIN 做横向分析
```

核心字段：

```text
UUID
HAS_MANUAL_INTERVENTION
FIRST_MANUAL_TIME
FIRST_BOT_TIME
LAST_BOT_TIME
HAS_MANUAL_TO_BOT
HAS_MANUAL_TO_BOT_ENTRY
HAS_BOT_TO_MANUAL
HAS_BOT_MANUAL_BOT
```

成长点：

- 数据分析不等于所有逻辑都塞进一条 SQL。
- 当 SQL 超时，应该重新设计数据层，而不是继续堆嵌套。
- 流程先后关系适合预计算成 Case 级特征。

### 7. 校验并解释结果

至少检查：

1. Phase 过滤器是否在所有组件一致。
2. 分子和分母是否属于同一范围。
3. 分类合计是否回到总 Case。
4. JOIN 是否放大数据。
5. 同一最大时间点多条 Activity 是否重复计数。
6. 终点 Activity 是否错误进入可回归分母。
7. NULL、空字符串和人工分类值是否被混淆。
8. 字段的业务含义是否被错用。

本轮典型错误与修正：

- 把 `BLANK` 当成 OCR Feedback 空值；实际它是人工设定的有效分类。
- 假设 OCR Feedback 可以解释 rerun 失败；实际它只解释初始不能 RPA。
- 使用 `INNER JOIN manual_reason_tbl` 导致 SUCCESS 全部被过滤。
- 把 Comments 当成全量属性；实际 Comments 更偏向异常、失败和停滞场景。
- 不同组件 Phase 过滤器不一致，导致 473 / 21,435 与 337 / 12,504 混用。
- 把人工录入完成放进回归分母，导致回归率失真。

### 8. 输出行动建议与提升机会

每个结论必须落到三类行动：

#### 业务规则

- 哪些问题必须人工确认？
- 哪些 QA、收货、电子签章规则可以标准化？
- 哪些场景应明确排除 RPA 范围？

#### 系统与数据

- PO、OU、供应商、金额、收货信息能否提前校验？
- BOT 错误码是否足够清晰？
- 人工修改后是否能生成可被 BOT 识别的结构化状态？

#### 流程设计

- 意见征询结束后是否自动回流？
- OCR完成后是否自动重新排队？
- 人工修改 PO、补充收货、完成电子签章后是否自动触发 rerun？
- 失败后是否有自动重试次数和退出条件？

最终不只说“某类问题很多”，而要回答：

```text
修复该类问题后，预计能增加多少 BOT 成功 Case？
```

## 本轮 Phase2 已验证结果

### 总体

- Phase2 总 Case：21,578
- RPA_PROCESS：11,520，53.388%
- MANUAL_PROCESS：9,735，45.115%
- 未明确归类：323，1.497%

### 路径漏斗

- 发生审批外人工介入：12,504
- 可回归人工 Case：4,902
- 人工后重新出现 BOT：328，6.691%
- 全部人工后回 BOT：337
- 最终 BOT 录入完成：92
- 真正人工后恢复自动录入：92 / 4,902，约 1.877%

### 人工 Activity

- 录入完成：9,716
- 意见征询：3,182
- OCR完成：2,064
- 废弃删除：59
- OCR待处理：7
- RPA范围外：3

### 可回归节点

- 意见征询：228 / 3,182，7.165%
- OCR完成：220 / 2,064，10.658%
- 同时包含意见征询和 OCR完成并回 BOT：120
- 仅意见征询并回 BOT：108
- 仅 OCR完成并回 BOT：100

### 最终 BOT 状态

- 录入中发生错误：116，34.421%
- 录入完成：92，27.299%
- 意见征询：84，24.925%
- 其他异常或待查：45

### 当前可解释的业务价值

1. 人工后真正恢复自动录入的比例很低，只有约 1.877%。
2. rerun 机会高度集中在意见征询和 OCR完成节点。
3. BOT 被重新触发后，失败和停滞多于成功。
4. PO号码/OU、QA、收货问题更偏向再次失败。
5. 电子签章、金额/单价和类型匹配更偏向意见征询停滞。
6. SUCCESS 组没有匹配到 Comments，说明成功组需要通过人工 Activity、结构化业务字段和流程状态解释，而不是强行用 Comments 解释。

## 下一轮分析顺序

1. 以 SUCCESS / FAILED / STALLED 为结果组。
2. 横向比较人工 Activity 和最后一次人工动作。
3. 对 FAILED / STALLED 使用 Comments 分类解释。
4. 关联 PO Result、PO Match Result、Request Type、System、Reworks。
5. 找到“件数高 + 可修复 + 当前成功率低”的机会项。
6. 估算规则修复、自动回流或自动重试后的提升 Case 数。

## 成长循环

```text
明确业务决策
→ 分开因果链
→ 固定口径
→ 建立流程漏斗
→ 构造结果组
→ 解释差异
→ 验证业务假设
→ 提出改善动作
→ 估算提升机会
→ 沉淀方法
```

## 当前能力升级目标

- 从“会写 SQL”升级到“会设计分析数据层”。
- 从“做图表”升级到“构建因果证据链”。
- 从“展示件数”升级到“解释为什么以及改哪里”。
- 从“发现异常”升级到“估算可提升的 Case 数”。
- 从“把字段都关联起来”升级到“理解每个字段在业务因果链中的正确位置”。
