# 自我成长模式

这个模式不是只把 SQL 跑通，而是让每次分析都沉淀成下一次可复用的能力。

## 一轮分析的六个步骤

### 1. 明确问题

先写清楚业务问题，不直接从图表或 SQL 开始。

示例：

- 哪些原因导致 EBS 大于阈值后需要人工检查？
- 哪些原因件数高但处理时间短？
- 哪些原因 Rework 高且最终无法恢复 RPA？

### 2. 固定口径

每次都明确：

- 基数是什么：Case、事件行、Status 行还是去重 UUID
- 是否排除 DDD
- 是否按 `OCR_FEEDBACK` 筛选
- 同一 UUID 是否允许进入多个分类
- 百分比分母是什么

### 3. 提出假设

先写出可验证的判断，例如：

- 收货和 PO 异常可能是 EBS 大于阈值的主要来源。
- 意见征询可能是处理节点，不一定是根因。
- 更改 PO 后部分 Case 仍有机会恢复 RPA。

### 4. 用 SQL 验证

SQL 输出至少包含：

- 分类
- Case 数或 Status 行数
- 占比
- 平均或中位处理时长
- Rework 率
- 最终 RPA 恢复率

原则：

- 具体规则优先，通用规则靠后。
- 使用 `LIKE / NOT LIKE` 时防止同一 Status 重复命中。
- 关联属性表时先对 UUID 去重，避免 JOIN 放大。
- IPM 2.0.3 中避免使用 `WITH`。

### 5. 校验结果

至少做四项检查：

1. 分类合计是否符合预期基数。
2. 同一 Status 是否重复命中。
3. JOIN 前后件数是否被放大。
4. Excel 与 IPM 的统计口径是否一致。

### 6. 沉淀与下一步

每轮结束记录：

```text
日期：
问题：
数据范围：
统计口径：
假设：
使用 SQL：
验证结果：
发现：
失败或误区：
下一步：
```

## 成长循环

```text
发现问题
→ 明确口径
→ 写 SQL
→ 校验
→ 解释业务原因
→ 提出优化建议
→ 沉淀方法
→ 下一轮提出更好的问题
```

## 当前项目的成长重点

- 从“展示件数”升级到“解释影响”。
- 从“单一分类图”升级到“原因 × 时长 × Rework × RPA恢复率”。
- 从“SQL能运行”升级到“口径可验证、逻辑可复用”。
- 从“发现异常”升级到“给出业务、系统、流程三类改善建议”。
