# 自我成长模式

这个模式不是只把 SQL 跑通，而是让每次分析都沉淀成下一次可复用的能力。

## 一轮分析的九个步骤

### 1. 先定义真正的业务问题

不要从“做哪张图”开始，而要从“客户要做什么决定”开始。

本项目真正要回答：

```text
为什么一开始不能 RPA？
人工处理后做了什么？
为什么有些 Case 能 rerun 成功，有些再次失败或停滞？
是否存在机器人重复失败和资源浪费？
修复哪一类问题最能提升 RPA、缩短时间、节省资源？
```

### 2. 分开两条因果链

#### 初始不能 RPA

重点字段：OCR Feedback、System、Request Type、PO Result、PO Match Result、票据类型与阈值。

#### 人工后 rerun

重点字段：人工 Activity、Comments 原因、是否更改 PO、补收货、完成签章、通过 QA、是否重新触发 BOT、最后一个 BOT Activity。

不能把 OCR Feedback 直接当成 rerun 失败原因，也不能把 Comments 当成全量属性。

### 3. 固定统计口径

每次明确：

- 基数是 Case 还是事件
- 是否排除 DDD
- 是否限定 Phase
- 分母是否包含终点 Activity
- “出现 BOT”“回到 BOT”“最终成功”分别如何定义
- 同一 UUID 是否允许进入多个分类
- 是否存在少量 Case 产生大量事件

新增重要认识：

```text
Case 数正常
不代表事件量正常
```

流程分析必须同时检查 Case 级和事件级异常。

### 4. 先构造流程漏斗，再做根因分析

推荐顺序：

```text
总体 RPA / 人工结果
→ 人工介入
→ 可回归人工 Case
→ 回到 BOT
→ 最终 BOT 状态
→ 事件级路径
→ 原因与属性
→ 改善动作
```

### 5. 提出可验证假设

示例：

- 意见征询和 OCR完成是主要可回归节点。
- 意见征询后 rerun 的主要问题是再次报错和再次意见征询。
- 人工修复结果未被结构化写回。
- BOT 缺少重试上限、冷却时间和相同错误去重。
- 少量 Case 可能消耗大量 BOT 资源。

每个假设都要有分子、分母、路径条件和对照组。

### 6. 选择合适的数据处理层

IPM 用于展示与交互，复杂时间先后逻辑用 Power Query 或数据源端预计算。

本轮使用：

```text
Excel Power Query
→ bot_recovery_case_tbl
→ IPM简单JOIN
→ Case清单
→ 单Case事件明细
```

成长点：

- SQL 超时应重新设计数据层。
- 流程先后关系适合预计算。
- 150行限制下，应先筛 Case，再看单 Case 明细。

### 7. 从聚合走到事件级诊断

聚合结果告诉我们“哪里有问题”，事件明细告诉我们“具体怎么发生”。

本轮观察到三种典型路径：

```text
人工意见征询
→ 机器人录入报错
→ 人工完成
```

```text
人工意见征询
→ 机器人多次意见征询
→ 人工完成
```

```text
人工意见征询
→ 机器人连续大量录入报错
```

101件机器人录入报错 Case 共出现750次报错事件，其中2件超过50次的 Case 共产生603次，占80.4%。这说明少量 Case 存在局部重试失控。

### 8. 校验并解释结果

必须检查：

1. Phase过滤器一致。
2. 分子分母同范围。
3. 分类合计回到总Case。
4. JOIN不放大。
5. 同一时间多活动不重复归类。
6. 终点活动不进入可回归分母。
7. BLANK与NULL不混淆。
8. 字段业务含义不误用。
9. 单Case事件数是否异常。
10. 是否存在高频重复错误、重试循环和机器人资源浪费。
11. SQL函数是否符合当前 IBM Process Mining 版本。

#### 本轮新增错误：时间字段转换写法错误

错误写法：

```sql
TO_TIMESTAMP(STARTTIME / 1000)
TO_CHAR(...)
```

IBM Process Mining 2.0.3 的 Advanced edit mode 使用 MonetDB 语法。官方文档示例使用：

```sql
sys.epoch(STARTTIME / 1000)
```

正确处理方式：

1. 毫秒时间戳除以1000。
2. 使用 `sys.epoch()` 转成日期时间。
3. 在 Elastic Widget 中把该列类型设置为 `datetime`。
4. 年月日分组使用 `EXTRACT(... FROM sys.epoch(...))`。

成长要求：涉及版本相关函数时，不能凭其他数据库经验直接写 SQL，必须先查当前版本文档。

### 9. 输出可执行价值

数据分析价值分四层：

#### 第一层：事实

- 有多少Case
- 比例是多少
- 路径在哪里

#### 第二层：诊断

- 为什么失败
- 在哪个节点失败
- 是业务问题、数据问题还是系统问题

#### 第三层：行动

- 改规则
- 改字段校验
- 改触发机制
- 改重试策略

#### 第四层：量化价值

- 可减少多少人工Case
- 可增加多少BOT成功Case
- 可减少多少重复事件
- 可节省多少BOT运行时间
- 可缩短多少等待时间

最终输出不能停在“发现问题”，而要形成：

```text
问题
→ 证据
→ 根因假设
→ 改善动作
→ 预期收益
→ 验证指标
```

### 总体

- 总Case：21,578
- RPA_PROCESS：11,520，53.388%
- MANUAL_PROCESS：9,735，45.115%
- 未明确归类：323，1.497%

### 路径漏斗

- 人工介入：12,504
- 可回归人工Case：4,902
- 人工后重新出现BOT：328，6.691%
- 全部人工后回BOT：337
- 最终BOT录入完成：92
- 真正恢复自动录入：92 / 4,902，约1.877%

### 意见征询路径

- 人工意见征询：3,182件
- 后续回机器人：228件
- 最终机器人录入完成：12件，5.263%
- 未完成的216件：
  - 机器人录入报错：101
  - 机器人最后仍为意见征询：84
  - OCR异常或待处理：29
  - RPA范围外：1

### 事件级异常

- 101件录入报错 Case 共产生750次报错事件。
- 2件超过50次的 Case 共产生603次，占80.4%。
- 说明可能缺少最大重试次数、错误去重、冷却时间、退出机制与Case锁。

## 作为数据分析专家应提供的价值

### 1. 不只报数，要指出业务风险

例如：

> 意见征询后228件回到机器人，但只有12件成功，说明当前回流机制有效性很低。

### 2. 不只找根因，要区分责任层

- 业务规则：是否满足rerun条件
- 数据质量：PO、OU、金额、收货是否完整
- 系统机制：错误码、重试上限、锁与冷却
- 流程设计：人工完成后是否自动回流

### 3. 不只给建议，要量化机会

建议建立机会表：

| 机会项 | 影响Case | 失败事件数 | 当前成功率 | 建议 | 预期价值 |
|---|---:|---:|---:|---|---|
| 意见征询后回流 | 228 | 待算 | 5.263% | 结构化完成标记+自动触发 | 提升成功率 |
| 录入错误重复重试 | 101 | 750 | 低 | 重试上限+去重+冷却 | 节省BOT资源 |
| PO/OU前置校验 | 待算 | 待算 | 低 | rerun前强校验 | 减少无效运行 |

### 4. 建立验证闭环

每项改善上线后都要追踪：

- rerun成功率
- 平均重试次数
- 单Case最大错误事件数
- 人工接管率
- 从意见征询到完成的时间
- BOT资源占用

## 下一轮分析顺序

1. 对高频报错 Case 结合 Event、Comments、PO、QA、签章字段做逐件诊断。
2. 区分一次失败与高频失败的业务属性。
3. 计算设置重试上限后可减少的无效事件数。
4. 分析意见征询到最终完成的耗时。
5. 形成“Case影响 + 事件浪费 + 流程时长 + 改善动作”的机会矩阵。

## 成长循环

```text
明确业务决策
→ 分开因果链
→ 固定口径
→ 建立漏斗
→ 事件级诊断
→ 解释根因
→ 设计动作
→ 量化价值
→ 上线验证
→ 沉淀方法
```
