# 会议记录：OCR反馈分析及后续工作规划

- 日期：2026-08-04
- 会议主题：OCR反馈分析及后续工作规划
- 业务代表：说话人3
- 目标：将当前 OCR Feedback 分类分析升级为可解释、可归责、可量化收益的业务诊断

## 一、会议总体结论

业务方认可当前方向，认为本轮分析相比上一次已经能够看到有价值的信息。

当前可继续沿用的分析入口：

- OCR Feedback Top 类型
- Status
- Comments / 留言分类
- PO Compare Result
- Prepayment Result
- 最终入账方式

但后续不能停留在单字段统计和饼图展示，需要通过多个字段组合回答：

```text
为什么 Case 停下来？
这次停顿是否合理？
责任属于客户、供应商、采购、人工操作还是机器人逻辑？
改善后可以节省多少 Working Hours？
```

## 二、业务方提出的核心判断

### 1. 人工介入不全部等于改善机会

业务方明确区分两类 Loss。

#### Nature Loss / 合理 Hard Stop

例如“大于阈值需检查”。

达到金额阈值后，业务必须检查合同、支持文档和付款条件。当前机器人无法读取和判断合同内容，因此人工检查属于制度和当前技术条件下必须存在的步骤。

这种情况即使出现人工介入，也不能简单判断为自动化失败。

#### 可改善的异常损耗

真正值得分析的是：

```text
人工检查
→ 发现合同、订单或支持材料问题
→ 发起意见征询
→ 等待回复
→ 再次检查
→ 再次入账
```

这段 Rework 才是后续 Saving 计算的重点。

### 2. “大于阈值需检查”必须继续拆原因

对该 OCR Feedback 不能只统计意见征询和废弃删除数量，还应继续判断具体原因。

#### 合同类问题

- 合同内容或格式问题
- 付款期限问题
- 支持文档缺失或不完整
- 验收相关问题
- 其他非 PO 类业务条件

业务含义：

机器人无法取消合同检查，但可以推动客户、供应商或业务用户第一次提交正确、完整的材料，从而减少后续 Rework。

#### PO / 订单类问题

- PO 未收货
- 收货不足
- 订单金额问题
- PO 信息错误
- 采购订单异常

业务含义：

问题更可能归属于采购团队、下单人员或客户订单质量，而不是合同检查本身。

### 3. PO 已匹配但仍停下来，是重点异常

业务方认为以下结果都可以视为 PO 基本正常：

- PO 可匹配单条
- PO 可匹配多条
- 金额匹配
- 单价匹配
- 类型匹配

这些结果可以合并为：

```text
PO_MATCH_OK
```

如果 PO 已匹配正常，但仍出现以下情况，则必须反查：

- 意见征询
- 废弃删除
- 最终人工入账
- 长时间停留

可能原因包括：

1. 大于阈值触发正常合同检查；
2. 电子签章、付款条件等其他非 PO 问题；
3. 机器人误判；
4. 人工错误操作；
5. 本应 RERUN 但未重新进入 BOT。

### 4. 匹配失败但最终正常完成，要反查机器人逻辑

对金额匹配失败、单价匹配失败、类型匹配失败等结果，需要拆成两个对照组：

```text
匹配失败 + 后续存在业务修正
匹配失败 + 无业务修正但最终完成
```

第一组更可能是真实业务问题。

第二组则可能属于：

- 机器人 False Negative
- 数据格式导致的假失败
- 容差或规则设置不合理
- 人可以稳定判断，但机器人判断失败

如果比例较高，应提交给 RPA 或开发团队进一步验证。

### 5. “无需核销”可能是规则自动化机会

预付款提示本身不一定有问题，但如果大量 Case 最终由人工判断为“无需核销”，则需要确认：

- 该结果是机器人给出的，还是人工给出的；
- 当前缺少哪些数据，导致机器人不能提前判断；
- 是否可以增加前置规则；
- 是否可以减少人工确认比例。

如果“无需核销”主要由人工判断，且规则逻辑稳定，则可能是较好的自动化优化方向。

### 6. 小额税差属于可接受损耗

税额相差 0.01、0.02、0.03 等情况，业务方解释为 Oracle 最后录入阶段的 rounding 问题。

处理原则：

- 合并成“税额舍入差异”；
- 不再按不同金额分别展示；
- 如果合计比例小，可作为可接受损耗；
- 如果比例高，再评估系统改造 ROI。

## 三、业务方要求的最终分析结构

### 第一层：High-level 自动化情况

建议展示：

- 总 Case 数
- RPA 完成比例
- 人工介入比例
- 最终人工入账比例
- 合理 Hard Stop 比例
- 异常 Rework 比例

### 第二层：改善问题分类

#### 客户 / 供应商输入问题

- 合同错误
- 支持文档不完整
- 付款条件错误
- 首次提交质量差

#### 采购 / 订单问题

- PO 未收货
- 收货不足
- 金额或 PO 信息错误

#### 机器人逻辑问题

- PO 正常但仍停下
- 匹配失败但无业务修正即可完成
- 本应 RERUN 却未回 BOT
- 人能稳定判断而机器人不能

#### 人工操作问题

- PO 正常但错误发起意见征询
- 人工处理路径偏离标准流程
- 不必要的人工入账

#### Nature Loss

- 合同强制检查
- 少量税额舍入
- 法规或制度要求的人工确认

### 第三层：Saving 计算

最终不建议直接对客户说“节省多少人”，而应优先输出：

```text
Estimated Working Hours Saving
```

建议公式：

```text
Saving Hours
= 减少的意见征询工时
+ 减少的 Follow-up 工时
+ 减少的二次检查工时
+ 减少的人工重新入账工时
```

注意：机器人运行和等待时间不能直接算成人工 Saving。

## 四、下一步五条分析线

### 分析线 1：大于阈值需检查的去向

拆分为：

- 检查后无异常，继续完成
- 合同类意见征询
- PO 类意见征询
- 废弃删除
- 最终人工入账
- 最终 BOT 入账
- 原因不明

目标：区分合理 Hard Stop 与实际 Rework。

### 分析线 2：PO 正常但仍停下

筛选 PO_MATCH_OK，再分析：

- 是否意见征询
- 是否废弃删除
- Comments 原因
- 最终人工还是 BOT

目标：识别机器人误判、人工误操作和流程未正确回流。

### 分析线 3：PO 匹配失败但最终无修正完成

对比：

- 有业务修正后完成
- 无业务修正但最终完成

目标：识别匹配逻辑 False Negative。

### 分析线 4：预付款无需核销

确认：

- 判断来源是机器人还是人工
- 人工判断比例
- 可用前置字段
- 是否可形成自动规则

### 分析线 5：Saving 模型

建议建立动作级标准工时：

| 动作 | 统计内容 |
|---|---|
| 发起意见征询 | 平均分钟 |
| Follow-up | 平均次数、平均分钟 |
| 二次检查 | 平均分钟 |
| 人工重新入账 | 平均分钟 |
| 废弃后重建 | 平均分钟 |

最终建议表结构：

| 问题类型 | Case 数 | 占比 | 平均额外人工时间 | 预计节省工时 | 责任团队 | 建议动作 |
|---|---:|---:|---:|---:|---|---|

## 五、重要分析约束

1. Blank 不能直接解释为“没有问题却人工处理”。
2. Blank 更准确的含义是“当前字段中未发现明确异常原因”。
3. 对 Blank Case 应抽样 UUID 向业务确认。
4. 不把所有人工介入都当成自动化损失。
5. 不把小数量异常直接列为优先改造项，应考虑 ROI。
6. 所有结论必须说明证据字段和判断逻辑。
7. 所有问题必须尽量映射到责任团队和后续动作。
