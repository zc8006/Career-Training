# Self Growth — 2026-08-04

## 本轮成长主题：从“分类统计”升级到“业务价值诊断”

这次会议最重要的成长，不是又增加了几个分析维度，而是开始真正理解：

```text
数据分析的价值不在于告诉业务“什么最多”，
而在于解释“为什么发生、是否合理、谁能改善、改善后值多少钱”。
```

## 一、过去容易停留在“数量视角”

之前的分析方式更偏向：

- OCR Feedback Top 1 / Top 2 / Top 3
- Status 分布
- Comments 分类占比
- PO Compare Result 分布
- 饼图和柱状图展示

这种分析可以回答：

```text
哪个问题最多？
```

但无法完整回答：

```text
这个问题是否真的需要改善？
为什么会发生？
责任属于谁？
改善后能省多少人工时间？
```

## 二、第一项能力升级：人工介入不等于自动化失败

过去容易把：

```text
出现人工 Activity
```

理解为：

```text
RPA 流程失败或存在改善空间
```

业务方明确指出，这个推断不成立。

例如“大于阈值需检查”属于 Hard Stop。合同检查在当前规则和技术条件下必须由人完成，因此这部分人工介入是 Nature Loss。

以后必须先区分：

```text
必要人工
异常人工
返工人工
最终人工入账
```

不能把四种不同含义合并成一个“人工率”。

## 三、第二项能力升级：从单字段分析转为组合证据链

单独看到：

```text
OCR Feedback = 大于阈值需检查
```

只能说明触发了某个检查点。

要判断业务含义，还需要组合：

```text
OCR Feedback
+ Status
+ PO Compare Result
+ Comments
+ 是否意见征询
+ 是否废弃删除
+ 是否 RERUN
+ 最终入账人
```

例如：

```text
大于阈值需检查
+ PO 匹配正常
+ 无意见征询
+ 最终 BOT 入账
```

更可能是合理合同检查。

而：

```text
大于阈值需检查
+ 合同类 Comment
+ 意见征询
+ 再次检查
+ 最终人工入账
```

则属于可改善 Rework。

以后每一个结论都应形成：

```text
现象 → 证据字段 → 业务解释 → 责任归属 → 改善动作
```

## 四、第三项能力升级：同时做正向和反向验证

过去更多是顺着异常分类继续下钻。

这次业务方给出的重要方法是双向验证。

### 正向验证

```text
业务结果异常
→ 后续是否真的发生业务修正？
```

例如金额匹配失败后，是否真的修改了 PO、金额或收货信息。

### 反向验证

```text
业务结果正常
→ 为什么仍然发生意见征询或人工入账？
```

例如：

```text
PO 可匹配
+ 金额匹配
+ 单价匹配
+ 类型匹配
+ 仍然意见征询
```

这类 Case 可能暴露：

- 机器人误判
- 人工误操作
- RERUN 逻辑缺失
- 状态与实际流程不一致

以后分析异常时，不只看“失败的 Case”，还要看：

```text
正常结果中的异常行为
异常结果中的正常完成
```

## 五、第四项能力升级：从根因分类进一步走向责任分类

业务方真正关心的不是复杂的 Comments 标签，而是：

```text
谁需要采取行动？
```

因此以后根因分类应继续映射为：

| 根因类别 | 责任对象 |
|---|---|
| 合同、支持材料、付款期限 | 客户 / 供应商 / 业务用户 |
| PO 未收货、收货不足、订单错误 | 采购团队 / 下单人员 |
| 匹配误判、未正确回 BOT | RPA / 开发团队 |
| 错误意见征询、异常人工操作 | IM / 业务操作团队 |
| 强制合同检查、小额 rounding | Nature Loss / 暂不改善 |

只有完成责任映射，分析结果才能进入行动阶段。

## 六、第五项能力升级：ROI 决定优先级

过去容易看到一个异常就认为应该改善。

业务方指出，小额税差虽然需要人工，但如果数量很少，系统改造可能无法通过 ROI。

以后需要同时考虑：

```text
Case 数量
× 单件人工工时
× 可消除比例
÷ 改造成本
```

分析结论应区分：

- 高价值优先改善
- 需要继续验证
- 可接受损耗
- 数量太少，暂不投入

不能只按数量排行，也不能只按“是否人工”排行。

## 七、第六项能力升级：Saving 应计算人工动作，而不是流程总时长

过去可能会使用：

```text
Case 数 × 平均处理天数
```

估算 Saving。

这种方法容易把机器人运行时间、等待时间和业务停留时间全部算成人工成本。

更合理的方式是按人工动作拆解：

```text
发起意见征询
Follow-up
二次检查
人工重新入账
废弃后重建
```

正式公式应更接近：

```text
Saving Hours
= 可减少的人工动作次数
× 对应动作平均工时
```

最终优先输出 Working Hours，而不是直接声称可以减少多少人。

## 八、对 Blank 的认识修正

内部讨论中曾倾向于把 Blank 理解为：

```text
没有任何问题但仍然人工入账
```

这个结论证据不足。

Blank 只能说明：

```text
当前已使用的字段中，没有发现明确异常原因
```

仍可能存在：

- 人工完成了必要合同检查；
- 问题记录在其他系统；
- Comment 未填写；
- 数据字段缺失；
- 正常检查后继续完成。

以后对 Blank 必须：

1. 保持中性命名；
2. 抽样 UUID；
3. 向业务确认；
4. 不提前给出异常结论。

## 九、今后的分析模板

每一条分析线都应按以下结构输出：

### 1. 现象

发生了什么？数量和比例是多少？

### 2. 证据

由哪些字段、Activity 和时间路径支持？

### 3. 业务判断

属于合理 Hard Stop、客户问题、采购问题、机器人问题还是人工问题？

### 4. 可改善性

是否可以通过流程、规则、数据或系统改造改善？

### 5. 收益

可减少哪些人工动作？预计节省多少 Working Hours？

### 6. 责任人与行动

谁需要继续验证或采取行动？

## 十、今后的自我约束

1. 不把人工介入直接解释成自动化失败。
2. 不把单字段分类直接解释成根因。
3. 不把 Blank 直接解释成“没有问题”。
4. 不把数量少的异常直接列为系统改造项。
5. 不用流程总时长代替人工 Saving。
6. 每个问题都要区分 Nature Loss 与可改善 Loss。
7. 每个结论都要形成字段证据链。
8. 同时做正向验证和反向验证。
9. 根因必须进一步映射责任团队。
10. 最终分析必须回答“改善后能带来什么价值”。

## 本轮能力升级总结

```text
分类统计
→ 多字段关联
→ 业务规则判断
→ 正反向异常验证
→ 根因与责任归属
→ ROI 与优先级
→ Working Hours Saving
```

这次成长的核心是：

```text
不要只做一张“数据看起来很丰富”的图，
而要建立一条从数据现象通向业务行动和价值的完整链路。
```
