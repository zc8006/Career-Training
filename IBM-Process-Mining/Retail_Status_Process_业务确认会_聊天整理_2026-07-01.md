## 1. 当前目标

本次 PPT 不是最终优化报告，而是业务确认会材料。核心是让业务确认：

1. 当前 eventlog 里的 Activity 分别代表什么业务状态。
2. 哪些状态是人工主导，哪些是系统/非人工主导，哪些是混合状态。
3. 当前 To-Be 流程草案是否可以作为后续 Reference Model 的基础。
4. 后续用业务标准流程对比实际 Case 流转偏差。

工作路线：

```text
看数据实际怎么走 → 问业务应该怎么走 → 做标准 Reference Model → 实际 Case vs 标准流程 → 找偏差最多/耗时最长/影响最大的路径 → 输出优化建议
```

## 5. Human / 非人工 Case 为什么会重叠

Human Rate 与 Robot / 非人工 Rate 不是互斥口径。

同一个 Case、同一个 Activity 下可能存在多条 eventlog 记录：

```text
caseid A | 意见征询 | 人工账号
caseid A | 意见征询 | 非人工账号 / 系统账号
```

因此该 Case 会同时被计入 Human Case 和非人工 Case。

例如：

```text
意见征询 Total Case = 3,915
Human Case = 3,915 → 100%
非人工 Case = 31 → 0.79%
```

解释：所有出现“意见征询”的 Case 都至少有人工账号参与，其中 31 个 Case 同时也出现非人工账号记录。所以不是 3,915 + 31，而是 31 与 3,915 有交集。

## 8. Activity 状态分类建议

| 类型 | Activity | 说明 |
|---|---|---|
| 人工主导 | OCR完成、意见征询、审批结束、审批拒绝、废弃删除 | Human Rate 接近或等于 100%，人工参与明显 |
| 系统/非人工主导 | OCR待处理、OCR结果有误、OCR结果待查、结果待查、录入中发生错误、OCR待处理/错误、RPA范围外 | Robot/System Rate 接近或等于 100%，偏系统判断或异常状态 |

建议颜色：

- 蓝色：人工主导
- 灰色：系统/非人工主导
- 橙色：混合状态
- 黄色菱形：业务判断网关

`录入完成` 不要涂成人工蓝色，建议橙色。`RPA范围外` 不要涂人工蓝色，建议灰色，标注“系统判断”。

## 9. As-Is 流程现状表达

建议 PPT 写法：

```text
当前 As-Is 流程中，除主线外还存在 OCR异常、结果待查、录入异常、RPA范围外、废弃删除等分支；部分 Case 在待查与异常状态之间重复流转。
```

“异常、待查、回退路径”的依据：

- 待查：`OCR结果待查`、`结果待查`
- 异常：`OCR结果有误`、`OCR待处理/错误`、`录入中发生错误`、`RPA范围外`、`废弃删除`、`审批拒绝`
- 回退/重复流转：节点之间出现交叉箭头、自循环，或者同一状态多次出现，例如 `录入中发生错误 → 录入中发生错误`。

更稳表达：

```text
当前 As-Is 流程中存在多条异常、待查与重复流转迹象，需要与业务确认各状态含义。
```

## 10. RPA范围外的分析结论

活动关系显示 `RPA范围外` 不是简单的流程起点，也不是纯人工入口。

先行作业：

```text
OCR待处理 → RPA范围外：635
录入中发生错误 → RPA范围外：20
OCR结果有误 → RPA范围外：9
RPA范围外 → RPA范围外：27
OCR完成 → RPA范围外：1
```

后继者：

```text
RPA范围外 → 录入完成：677
RPA范围外 → 审批结束：322
RPA范围外 → 意见征询：217
RPA范围外 → OCR结果有误：104
RPA范围外 → 废弃删除：37
RPA范围外 → 审批拒绝：16
RPA范围外 → OCR待处理：15
```

结论：

```text
RPA范围外并非单一前置判断状态。从活动关系看，它既可能由 OCR待处理、OCR结果有误、录入中发生错误等状态进入，也可能流向录入完成、意见征询、审批结束、废弃删除等多个后续状态，需要业务确认其真实含义。
```

核心问题：

```text
RPA范围外是在流程开始前判断出来的，还是系统/OCR处理过程中发现不满足规则后标记的？
RPA范围外之后，正常业务上应该进入人工录入、意见征询、审批，还是直接废弃？
```

`OCR完成` 也不是简单的 `OCR待处理 → OCR完成 → 录入完成`。

```text
OCR完成 → OCR完成：125

审批拒绝 → OCR完成：68
OCR结果有误 → OCR完成：47
RPA范围外 → OCR完成：23
OCR待处理 → OCR完成：1
```

OCR完成的后继者：

```text
OCR完成 → 审批结束：1,404
OCR完成 → 录入完成：295
OCR完成 → OCR完成：125
OCR完成 → 意见征询：76
```

## 12. 为什么线上的数字和节点 Case 数对不上

不能简单把前面分支件数相加去对 `录入完成` 的实际件数。

原因：流程图上的线/转换次数，和 Activity 节点的去重 Case 数不是一个口径。

线上的数字通常表示活动转换次数，不是去重 Case 数。

同一个 Case 可能多次进入 `录入完成`，也可能通过多条路径进入或回到 `录入完成`。

PPT 建议写法：

```text
从活动关系看，录入完成是多个路径的关键汇合状态。
但流程图中连线数字表示活动转换次数，节点 Case 数为去重后的 Case 数。
由于同一 Case 可能在待查、异常和录入完成之间重复流转，因此各进入路径不能直接相加等于录入完成件数。
```

另外，`OCR结果待查` 节点数很大，建议单独标注：

```text
OCR结果待查存在明显重复流转，需要后续进一步确认是否为系统重复写入、重试机制或业务反复待查。
```

## 13. To-Be 流程草案

To-Be 不要强行复现 As-Is，因为 As-Is 本身存在交叉流转和重复流转。

To-Be 应该是：业务认可的标准流程。

推荐草案：

```text
Start
↓
是否满足RPA/OCR处理规则？
├─ 否 → RPA范围外 → 是否可转人工处理？
│                    ├─ 是 → 录入完成
│                    └─ 否 → 废弃删除
└─ 是 → OCR待处理
        ↓
      OCR完成
        ↓
      OCR结果是否正常？
      ├─ 正常 → 录入完成
      ├─ 结果异常 → OCR结果有误 → OCR结果待查 → 结果待查
      └─ 处理错误 → OCR待处理/错误 → OCR结果待查 → 结果待查

结果待查
↓
是否发生录入异常？
├─ 否 → 录入完成
└─ 是 → 录入中发生错误 → 异常是否可处理？
                         ├─ 是 → 录入完成
                         └─ 否 → 废弃删除

录入完成
↓
是否进入审批相关流程？
├─ 否 → End
└─ 是 → 是否需要意见征询？
        ├─ 是 → 意见征询 → 审批结果判断
        └─ 否 → 审批结果判断

审批结果判断
├─ 通过 → 审批结束 → End
├─ 拒绝 → 审批拒绝 → End
└─ 废弃 → 废弃删除 → End
```

## 14. BPMN 画法注意事项

1. 判断条件使用菱形网关。
2. 实际 Activity 使用矩形活动框。
3. `处理后完成`、`无法处理` 不要作为活动框，应该作为连线标签。
4. `录入中发生错误` 是数据里的状态，可以作为活动框。
5. `异常是否可处理？` 应该是菱形。
6. `RPA范围外` 后建议加一个判断：`是否可转人工处理？`
7. `审批结束`、`审批拒绝`、`废弃删除` 都可以直接接 End，不要绕大圈。

```text
OCR完成 的真实含义是什么？是系统 OCR 自动完成，还是人工确认/补充处理完成？
```



```text
业务最关心的问题是效率、异常率、人工介入、审批周期，还是废弃/拒绝原因？
```

```text

3. OCR结果待查 和 结果待查 有什么区别？
4. 录入中发生错误 是否确认是系统异常？
5. 录入完成 是否需要拆成人工完成和系统完成？
6. 废弃删除 是审批结果，还是异常阶段也可能发生？
```

## 17. PPT 问题回答完之后做什么

如果业务回答了 PPT 里的问题，下一步不要马上写优化建议，而是先固化流程口径。

步骤：

1. 整理会议确认结果表。
2. 根据业务确认结果调整 To-Be BPMN。
3. 重新定义 Activity 分类：人工 / 系统非人工 / 混合。
4. 根据业务提供的账号信息修正数据口径。
5. 上传或重建 Reference Model，做一致性检查。
6. 找出偏差最多、耗时最长、影响最大的 Case。
7. 再输出优化建议。

会议确认结果表建议字段：

| 确认项 | 当前数据判断 | 业务确认结果 | 后续处理 |
|---|---|---|---|
| RPA范围外 | 系统/非人工记录为主 | 待确认 | 决定放在前置判断还是异常分支 |
| OCR完成 | Human Rate 100%，但路径来源复杂 | 待确认 | 决定是否改名/单独说明 |
| 录入中发生错误 | 非人工 100% | 待确认 | 保留为系统异常节点 |
| 录入完成 | 混合状态 | 待确认 | 是否拆成系统录入完成/人工录入完成 |
| 意见征询 | 人工 100% | 待确认 | 决定审批前置逻辑 |
| 废弃删除 | 人工主导 | 待确认 | 决定是否多个入口进入废弃删除 |

---

## 18. 最终理解

重点不是单纯画流程，而是：

```text
拿业务认可的标准流程，去对比 eventlog 里实际 Case 的流转偏差。
```

PPT 这些问题如果业务都回答清楚，基本能明白流程主干、例外路径、系统状态和人工状态。  
但真正的业务问题，要靠下一步的偏差 Case 分析才能挖出来。

这份文档用于换窗口后接续本次分析。
