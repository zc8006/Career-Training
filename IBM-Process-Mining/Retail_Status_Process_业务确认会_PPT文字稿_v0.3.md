## 第 2 页｜会议目标

本次会议主要确认三件事：

1. 当前事件日志中各 Activity 的业务含义是否理解正确。
2. 人工账号、系统/机器人账号的统计口径是否符合业务实际。
3. 基于数据整理出的 To-Be 参考流程是否可以作为后续 Reference Model 的基础。

**期望输出：**

- 确认 RPA 范围外、OCR 待查、录入异常、意见征询、审批结束/拒绝等状态含义。
- 确认哪些节点属于人工主导，哪些属于系统/非人工主导，哪些属于混合状态。
- 明确下一步需要调整的数据口径、流程模型和一致性检查方向。

**分析范围：**

- Phase1：2024/11 – 2025/07
- Phase2：2025/10 – 2026/05

**核心统计口径：**

- Case 数：按 `eventlog.caseid` 去重统计。
- Activity：使用事件日志中的原始状态名称。
- 人工参与：`resource` 属于人工账号清单。
- 非人工/系统参与：`resource` 不属于人工账号清单。

**注意事项：**

Human Case 与 Robot/System Case 不是互斥口径。同一个 Case 在同一个 Activity 下可能同时存在人工账号和非人工账号记录，因此两类比例相加不一定等于 100%。

## 第 7 页｜系统/非人工参与状态分析

**截图占位：机器人/非人工参与的状态表**

**当前数据结论：**

系统/非人工参与明显的状态包括：

- OCR待处理/错误：Robot/System Rate 100%
- 录入中发生错误：Robot/System Rate 100%
- RPA范围外：Robot/System Rate 100%
- OCR结果有误：Robot/System Rate 100%
- OCR结果待查：Robot/System Rate 100%
- 结果待查：Robot/System Rate 100%
- OCR待处理：Robot/System Rate 99.24%

**初步判断：**

这些状态更像系统判断、系统异常、OCR异常或待查状态，而不是人工实际处理动作。

特别注意：

- `RPA范围外` 从业务含义看可能会转人工处理，但该状态本身几乎全部由非人工账号记录。
- 因此建议在流程图中将 `RPA范围外` 标为“系统判断”，后续分支可标注“转人工处理”。

## 第 8 页｜Activity 状态分类建议

| 类型 | Activity | 说明 |
|---|---|---|
| 人工主导 | OCR完成、意见征询、审批结束、审批拒绝、废弃删除 | Human Rate 接近或等于 100%，人工参与明显 |
| 系统/非人工主导 | OCR待处理、OCR结果有误、OCR结果待查、结果待查、录入中发生错误、OCR待处理/错误、RPA范围外 | Robot/System Rate 接近或等于 100%，偏系统判断或异常状态 |
| 混合状态 | 录入完成 | Human Rate 82.1%，Robot/System Rate 18.35%，人工和系统均有参与 |

**建议颜色：**

- 蓝色：人工主导
- 灰色：系统/非人工主导
- 橙色：混合状态
- 黄色菱形：业务判断网关

## 第 10 页｜To-Be 参考流程草案

**截图占位：重新整理后的 To-Be BPMN 流程图**

**建议流程主线：**

1. 是否在 RPA 处理范围内？
2. OCR待处理 → OCR完成
3. OCR结果是否正常？
   - 结果正常 → 录入完成
   - 结果异常 → OCR结果有误 → OCR结果待查 → 结果待查
   - 处理错误 → OCR待处理/错误 → OCR结果待查 → 结果待查
4. 结果待查后判断是否发生录入异常
   - 否 → 录入完成
   - 是 → 录入中发生错误 → 判断异常是否可处理
5. 录入完成后判断是否进入审批相关流程
6. 如需审批，判断是否需要意见征询
7. 审批结果判断：通过、拒绝、废弃

**建模原则：**

- 矩形节点尽量使用 eventlog 中的原始 Activity 名称。
- 菱形网关使用业务判断语言。
- 分支条件使用“是/否、通过/拒绝、可处理/无法处理”等标签。

## 第 11 页｜需要业务确认的问题

1. `RPA范围外` 是否表示系统判断无法自动处理，然后转人工处理？
2. `OCR完成` 为什么在日志中几乎全部由人工账号记录？它是否代表人工确认？
3. `OCR结果待查` 与 `结果待查` 的区别是什么？是否都属于系统待查状态？
4. `录入中发生错误` 是否确认是系统录入异常，而不是人工录入错误？
5. `录入完成` 中人工与系统分别对应哪些场景？
6. 哪些 Case 在 `录入完成` 后不需要进入审批流程？
7. `意见征询` 是否一定发生在审批之前？
8. `废弃删除` 是审批结果分支，还是在异常处理阶段也可能发生？
9. 当前人工账号清单是否完整？是否存在遗漏的系统账号或人工账号？
10. Phase2 比例下降或路径变化，是否符合业务预期？

## 第 12 页｜下一步计划

**短期：业务确认后调整分析口径**

- 修正人工账号/系统账号清单。
- 确认 Activity 的业务含义。
- 对 RPA范围外、录入异常、待查状态等关键节点重新归类。

**中期：调整 To-Be Reference Model**

- 根据业务反馈修正 BPMN。
- 保留与 eventlog 匹配的原始 Activity 名称。
- 上传 Reference Model，执行模型一致性检查。

**后续：输出优化建议**

- 识别主要偏差路径。
- 分析重复待查、录入异常、意见征询等高频问题。
- 输出可落地的流程优化点和规则优化建议。

## 第 13 页｜总结

本次分析不是为了直接判定流程问题，而是先用数据帮助业务确认流程事实：

- 哪些状态是人工主导？
- 哪些状态是系统/非人工主导？
- 哪些状态是混合状态？
- 当前流程中的异常、待查和审批路径是否符合业务实际？

确认后，下一步将基于业务认可的 To-Be 流程作为 Reference Model，继续进行一致性检查和流程优化分析。
